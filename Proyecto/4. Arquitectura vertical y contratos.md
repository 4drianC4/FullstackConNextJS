## Estructura de la aplicación

```text
src/
  app/
    api/events/route.ts
    api/auth/[...nextauth]/route.ts
    dashboard/events/page.tsx
    login/page.tsx
  features/
    users/
    events/
      shared/event.schema.ts
      backend/event.service.ts
      backend/event.controller.ts
      frontend/event-form.tsx
    admissions/
    drinks/
    bar-sales/
    reservations/
  shared/
    lib/prisma.ts
    lib/api-error.ts
    lib/access.ts
    lib/permissions.ts
    ui/
  generated/prisma/
  types/next-auth.d.ts
  auth.ts
prisma/
  schema.prisma
  migrations/
  seed.ts
```

Las rutas HTTP y páginas delegan en una funcionalidad. Su backend no se importa desde frontend. `shared` dentro de una funcionalidad contiene contratos puros; `shared` en la raíz es infraestructura y UI transversal. No añadir repositorios, fábricas y contenedores de inyección solo para cumplir un patrón.

## Dirección de las dependencias

Ruta HTTP → guard/controlador → esquema y servicio → Prisma. Página → componente de funcionalidad → contrato público/API. Un componente servidor puede llamar un servicio después de autorizar; no necesita un fetch contra su propio servidor.

Un módulo puede necesitar datos de otro, pero no importa su componente visual ni modifica su estado arbitrariamente. Los IDs y FK se coordinan. El acceso compartido pasa por contratos acordados; los seeds permiten desarrollar contra datos válidos cuando otro equipo aún no terminó.

## Contratos HTTP

| Funcionalidad | Rutas orientativas | Reglas principales |
| --- | --- | --- |
| Usuarios | /api/users; /api/users/[id] | Sin registro público; selects sin hash; desactivar sin borrar historial |
| Eventos | /api/events; /api/events/[id] | DRAFT → OPEN → CLOSED; capacidad fija después de abrir |
| Entradas | /api/admissions; /api/admissions/[id]/check-in | Aforo atómico; ingreso único; sin cancelación en MVP |
| Bebidas | /api/categories; /api/drinks; /api/drinks/[id] | Centavos enteros, disponibilidad; no borrar referencias históricas |
| Ventas | /api/bar-sales; /api/bar-sales/[id] | Actor de sesión, total de servidor y clave idempotente |
| Reservas | /api/tables; /api/reservations; /api/reservations/[id] | Una mesa/evento; eliminación administrativa antes del evento |

GET lista/detalle, POST crea o ejecuta una acción explícita, PATCH edita y DELETE elimina donde esté permitido. La acción de check-in es POST, nunca GET. Error común `{ "error": "mensaje" }`, con `issues` opcional de validación; no devolver stack, SQL, cookies ni credenciales.

DTO de evento: `{ id, name, startsAt, capacity, status }`; fechas ISO. DTO de bebida: `{ id, name, categoryId, priceCents, available }`. La emisión recibe `{ eventId, holderName }`; el servidor fija ID, contador y estado. La venta recibe `{ requestKey, items: [{ drinkId, quantity }] }`; no recibe total ni actor confiables. La reserva recibe `{ eventId, tableId, guestName }`.

## Permisos

| Operación | ADMIN | STAFF |
| --- | --- | --- |
| Administrar cuentas y roles | Sí | No |
| Crear/editar eventos, bebidas, categorías y mesas | Sí | No |
| Consultar eventos, bebidas y mesas | Sí | Sí |
| Emitir entradas y registrar ingreso | Sí | Sí |
| Crear y consultar ventas | Sí | Sí |
| Crear y consultar reservas | Sí | Sí |
| Eliminar una reserva antes del evento | Sí | No |

No hay recursos privados de clientes en el MVP: es una aplicación interna. Si se amplía con clientes, añadir control por propietario; un ID difícil de adivinar no es una autorización.

## Migraciones e integración

Acordar modelo común al día 4. Cada cambio de esquema necesita revisión del instructor; integrar sobre main actualizado y comprobar migraciones en una base limpia. No editar una migración ya aplicada para resolver un conflicto, ni ejecutar `migrate reset` sobre datos compartidos.

Los mocks están identificados y respetan el contrato; desaparecen del recorrido final. La API usa datos de prueba reales de PostgreSQL cuando hay FK. Un contrato no hace independiente una operación que realmente necesita la identidad o el evento.
