## Esquema común del MVP

Copiar este esquema al repositorio de aplicación, no crear seis bases distintas. Los equipos proponen ampliaciones mediante PR coordinados.

```prisma
generator client {
  provider = "prisma-client"
  output   = "../src/generated/prisma"
}
datasource db {
  provider = "postgresql"
}
enum Role {
  ADMIN
  STAFF
}
enum EventStatus {
  DRAFT
  OPEN
  CLOSED
}
model User {
  id           String    @id @default(uuid())
  name         String
  email        String    @unique
  passwordHash String
  role         Role      @default(STAFF)
  active       Boolean   @default(true)
  sales        BarSale[]
  createdAt    DateTime  @default(now())
  updatedAt    DateTime  @updatedAt
}
model Event {
  id             String       @id @default(uuid())
  name           String
  startsAt       DateTime
  capacity       Int
  admissionCount Int          @default(0)
  status         EventStatus  @default(DRAFT)
  admissions     Admission[]
  reservations   Reservation[]
  createdAt      DateTime     @default(now())
  updatedAt      DateTime     @updatedAt
}
model Admission {
  id          String    @id @default(uuid())
  eventId     String
  event       Event     @relation(fields: [eventId], references: [id], onDelete: Restrict)
  holderName  String
  checkedInAt DateTime?
  createdAt   DateTime  @default(now())
  @@index([eventId])
}
model Category {
  id        String  @id @default(uuid())
  name      String  @unique
  drinks    Drink[]
}
model Drink {
  id         String        @id @default(uuid())
  name       String
  categoryId String
  category   Category      @relation(fields: [categoryId], references: [id], onDelete: Restrict)
  priceCents Int
  available  Boolean       @default(true)
  saleItems  BarSaleItem[]
  createdAt  DateTime      @default(now())
  updatedAt  DateTime      @updatedAt
  @@index([categoryId])
}
model BarSale {
  id          String        @id @default(uuid())
  requestKey  String        @unique
  requestHash String
  totalCents  Int
  createdById String
  createdBy   User          @relation(fields: [createdById], references: [id], onDelete: Restrict)
  items       BarSaleItem[]
  createdAt   DateTime      @default(now())
  @@index([createdAt])
}
model BarSaleItem {
  id             String   @id @default(uuid())
  saleId         String
  sale           BarSale  @relation(fields: [saleId], references: [id], onDelete: Restrict)
  drinkId        String
  drink          Drink    @relation(fields: [drinkId], references: [id], onDelete: Restrict)
  quantity       Int
  unitPriceCents Int
}
model ClubTable {
  id           String        @id @default(uuid())
  number       Int           @unique
  capacity     Int
  reservations Reservation[]
}
model Reservation {
  id        String    @id @default(uuid())
  eventId   String
  event     Event     @relation(fields: [eventId], references: [id], onDelete: Restrict)
  tableId   String
  table     ClubTable @relation(fields: [tableId], references: [id], onDelete: Restrict)
  guestName String
  createdAt DateTime  @default(now())
  @@unique([eventId, tableId])
}
```

## Reglas que el esquema no expresa solo

- Capacidad y cantidades positivas, centavos no negativos y total dentro del rango Int de PostgreSQL. Aplicar límites Zod y cálculos seguros; no basta `number`.
- Capacidad fija al salir de DRAFT; transición de estados validada atómicamente. Las reservas no reducen el contador de entradas.
- Apertura y cierre de evento autorizados; emisión con actualización condicional dentro de una transacción.
- `checkedInAt` solo cambia de null a fecha mediante el servicio de ingreso.
- No borrar ventas ni entradas en el MVP; desactivar usuarios y bebidas evita romper referencias.
- Reserva eliminable por ADMIN antes de la fecha del evento. La ampliación de cancelación con historial necesita otro diseño.

No usar soft delete para todas las tablas por costumbre: elegir según el historial y las restricciones que se necesitan conservar.

## Seed reproducible

`prisma/seed.ts` usa un cliente propio de script, no el módulo `server-only` de Next.js:

```ts
import "dotenv/config";
import { PrismaClient } from "../src/generated/prisma/client";
import { PrismaPg } from "@prisma/adapter-pg";
import bcrypt from "bcryptjs";
const url = process.env.DATABASE_URL;
if (!url) throw new Error("Falta DATABASE_URL");
const prisma = new PrismaClient({ adapter: new PrismaPg({ connectionString: url }) });
async function main() {
  const email = process.env.SEED_ADMIN_EMAIL?.toLowerCase();
  const password = process.env.SEED_ADMIN_PASSWORD;
  if (!email || !password || password.length < 8 || new TextEncoder().encode(password).length > 72)
    throw new Error("Define credenciales locales de seed: contraseña entre 8 caracteres y 72 bytes");
  await prisma.user.upsert({
    where: { email }, update: {},
    create: { email, name: "Administración demo", role: "ADMIN", passwordHash: await bcrypt.hash(password, 12) },
  });
  await prisma.event.upsert({
    where: { id: "00000000-0000-4000-8000-000000000001" }, update: {},
    create: { id: "00000000-0000-4000-8000-000000000001", name: "Noche de prueba", startsAt: new Date("2026-12-05T22:00:00-04:00"), capacity: 100, status: "OPEN" },
  });
  const category = await prisma.category.upsert({
    where: { name: "Sin alcohol" }, update: {}, create: { name: "Sin alcohol" },
  });
  await prisma.drink.upsert({
    where: { id: "00000000-0000-4000-8000-000000000002" }, update: {},
    create: { id: "00000000-0000-4000-8000-000000000002", name: "Agua", priceCents: 1000, categoryId: category.id },
  });
  await prisma.clubTable.upsert({
    where: { number: 1 }, update: {}, create: { number: 1, capacity: 4 },
  });
}
main().catch(() => {
  console.error("Seed fallido; revisar configuración local sin imprimir secretos");
  process.exitCode = 1;
}).finally(async () => { await prisma.$disconnect(); });
```

Es un seed de desarrollo. No cambia la contraseña del administrador existente ni reinicia contadores. Añadir usuarios STAFF de test con variables propias y datos de cada equipo. Actualizar la fecha sintética si quedó en el pasado. No ejecutar el seed completo contra producción.

## Venta idempotente: algoritmo del módulo

1. Validar `requestKey` UUID y 1–50 líneas, cantidades 1–100. Agrupar bebidas repetidas, ordenar por ID y rechazar cantidades agregadas fuera de rango.
2. Obtener el actor desde sesión; calcular SHA-256 de un JSON canónico de **actor + líneas ordenadas**, sin total ni secretos. El hash es para comparar pedidos, no para guardar contraseñas.
3. Buscar `requestKey`: si existe y actor/hash coinciden, devolver la misma venta. Si difieren, 409 sin revelar la venta ajena.
4. En una transacción consultar bebidas disponibles, comprobar que existen todas, calcular precios y total y crear cabecera y líneas. Guardar `requestHash`, `requestKey` y precios históricos.
5. Ante P2002 por carrera en `requestKey`, volver a consultar y aplicar la misma comparación; no crear otra clave silenciosamente.
6. El navegador conserva la clave y el mismo contenido durante un reintento incierto. Generar una nueva clave solo para una nueva venta; editar un pedido pendiente exige resolver primero si el anterior se registró.

Los alumnos implementan este servicio como tarea guiada del módulo de ventas. Verificar con dos peticiones simultáneas y con la misma clave pero distinto contenido. Una transacción sin clave única no evita duplicados.
