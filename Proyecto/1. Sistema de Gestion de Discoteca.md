# Sistema de gestión de Discoteca

## Producto y límites

Una aplicación interna para personal de una discoteca. ADMIN administra cuentas, eventos, bebidas y mesas. STAFF atiende entradas, ingreso, ventas y reservas. No hay registro público ni pagos bancarios; registrar una venta no implica procesar un cobro real.

El MVP tiene seis funcionalidades: usuarios, eventos, entradas, bebidas, ventas y reservas. No se requieren QR, inventario, facturación fiscal, reportes avanzados, pagos en línea, chat ni tiempo real. Los datos son de demostración.

## Recorridos principales

1. ADMIN crea y abre un evento; su capacidad queda fija tras abrirse.
2. STAFF emite una entrada si quedan plazas y registra su ingreso una sola vez.
3. ADMIN mantiene catálogo de bebidas; STAFF registra una venta cuyos precios calcula el servidor.
4. STAFF reserva una mesa para un evento; la base rechaza duplicados.
5. ADMIN desactiva una cuenta; las operaciones siguientes de esa cuenta se rechazan.

Las reservas de mesa no emiten entradas ni consumen el aforo del evento en este MVP. La capacidad se aplica a entradas emitidas. La reserva se libera eliminándola antes del evento, con permiso administrativo; cancelar y auditar reservas es ampliación.

## Forma de trabajo

Hasta seis equipos de tres. Cada integrante asume una tarea vertical: datos, endpoint y pantalla del mismo comportamiento. Todos trabajan en backend durante las primeras semanas y en frontend después. Las funciones se integran mediante PR, no mediante copias de carpetas al final.

El instructor coordina el modelo común, migraciones y contratos. Antes de tener autenticación solo se ejecutan las escrituras en local. Antes de publicar se exige el hito de permisos y pruebas. La aplicación se crea en otro repositorio.

## Reducir bloqueos

La identidad de usuario, eventos y bebidas son dependencias reales. El primer seed ofrece cuentas, eventos y catálogo sintéticos estables. Los equipos usan esos registros y mocks de interfaz compatibles con el contrato mientras esperan una integración. No se eliminan FK para aparentar independencia.

Si un equipo se retrasa, integrar fixtures mínimos o un adaptador temporal identificado, sin marcar la funcionalidad como terminada. Toda entrega final declara qué flujos siguen simulados.

## Éxito del proyecto

Un compañero puede reconstruir el entorno, autenticarse y completar el flujo del módulo con permisos correctos. La aplicación desplegada conserva datos y muestra errores comprensibles. Cada integrante explica su contribución y muestra pruebas y revisiones realizadas.
