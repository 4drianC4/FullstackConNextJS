# Guía de contribución y estándares del proyecto

[[README|Inicio]] · [[Proyecto/4. Arquitectura vertical y contratos|Arquitectura]] · [[Proyecto/5. Evaluacion y entregables|Evaluación]]

## Git y PR

`main` integra código revisado. Crear ramas `feat/events-create`, `fix/admissions-check-in`, `docs/setup`. Commits `feat: agrega creación de eventos`. Sincronizar antes de empezar y acordar conflictos; un compañero revisa y el instructor integra. No se introduce una rama dev adicional.

PR: problema, cambio observable, contrato/regla afectada, cómo se probó y limitaciones. Marcar si se usó IA y qué se corrigió. No incluir dumps de conversaciones ni secretos. Cada integrante revisa al menos dos PR de otros compañeros con evidencia de lectura/prueba.

## Código y arquitectura

TypeScript estricto, `unknown` para errores externos, sin `any`. camelCase para variables/funciones, PascalCase para tipos/componentes y kebab-case para archivos. Los archivos de clase en esta bóveda conservan CLASE N; esa convención es independiente de la aplicación.

Cada funcionalidad conserva backend, frontend y contratos. Importar servicios desde servidor, no desde cliente. Validar entradas, usar selects públicos y no convertir un body completo en `data` de Prisma. El servidor asigna actor y privilegios.

Usar nombres consistentes: `passwordHash`, `priceCents`, `unitPriceCents`, `totalCents`, `checkedInAt`. No intercambiar password/passwordHash ni pesos/centavos. Comentarios explican reglas y decisiones, no prometen seguridad absoluta.

## UI

Componentes comunes en `src/shared/ui`, configuración compatible de shadcn y Tailwind 4. Acento violeta, superficies oscuras, texto legible. Respetar foco, labels, teclado, estados vacíos y mensajes de error. No usar solo color para comunicar éxito o rechazo.

No es obligatorio tema alternable ni animación. Un formulario simple y usable tiene prioridad sobre una pantalla compleja incompleta.

## Controles

Ejecutar lint, typecheck, tests y build; probar el flujo y permisos por petición directa. Los logs de diagnóstico del servidor pueden ser necesarios; no prohibir todo log en producción, sino evitar datos privados y ruido. No incluir `console.log` de contraseñas, cookies o bodies sensibles.

Mantener `.env.example`, lockfile, migraciones y documentación; ignorar `.env` real. Los apuntes de esta bóveda no reciben credenciales de la aplicación ni de OpenCode.

## Definición de terminado

Contrato y permisos documentados, código integrado, pruebas relevantes, interfaz conectada, estados de error, instrucciones reproducibles y evidencia de revisión. No marcar como terminado lo que depende de un mock no declarado.
