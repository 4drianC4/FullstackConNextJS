# Metodología: Desarrollo por "Verticales" (Slices) y Code Review

## 1. Visión General del Proyecto
Construiremos desde cero un **Sistema de Gestión para Restaurante**. El sistema constará de varias áreas interconectadas: un panel de administración (Backoffice) para controlar el menú, las mesas, el inventario de cocina y los pedidos, y una experiencia de uso para el personal (meseros, cocina) y los clientes que reservan una mesa o consultan la carta.

El objetivo principal es simular un entorno de desarrollo profesional real. Todo el código se integrará en un único repositorio centralizado (Monorepo o Repositorio Unificado) en GitHub. Cada avance se trabajará en ramas independientes y deberá ser revisado, comentado y aprobado mediante *Pull Requests* antes de pasar a la rama principal.

## 2. Stack Tecnológico
Para garantizar homogeneidad en el aprendizaje y agilidad en el despliegue, utilizaremos un stack moderno basado íntegramente en JavaScript/TypeScript:

* **Frontend (Cliente):** Next.js (App Router), React, Tailwind CSS, Zustand (Manejo de estado global), React Hook Form + Zod (Validación de formularios).
* **Backend (Servidor):** Next.js (Route Handlers / API Routes), Node.js.
* **Base de Datos y ORM:** PostgreSQL (alojado en Supabase o Neon), Prisma ORM.
* **Autenticación:** NextAuth.js (Auth.js) con credenciales y roles.
* **Infraestructura y Herramientas:** Vercel (CI/CD y Hosting), GitHub (Control de versiones), Git, ESLint / Prettier.

## 3. Arquitectura y Metodología de Trabajo
Para evitar que el incumplimiento o retraso de un estudiante bloquee el progreso de los demás, aplicaremos el enfoque de **Desarrollo Vertical (Vertical Slices)**. Cada desarrollador será propietario de una funcionalidad completa de extremo a extremo (Fullstack): diseñará sus modelos en la base de datos, creará sus propios endpoints en la API y maquetará la interfaz correspondiente.

### El Flujo de Vida de una Tarea (Feature Branch Workflow)
1.  **Asignación:** El desarrollador recibe su módulo asignado con sus requerimientos mínimos.
2.  **Diseño DB (Aislado):** Modifica el archivo `schema.prisma` agregando únicamente las tablas o campos necesarios para su característica.
3.  **Backend:** Construye y prueba de forma aislada sus endpoints RESTful (POST, GET, PUT, DELETE) utilizando herramientas como Thunder Client o Postman.
4.  **Frontend:** Diseña y conecta los componentes visuales con la API que acaba de construir, gestionando los estados necesarios.
5.  **Integración:** Abre un *Pull Request (PR)* en GitHub. El código solo se unirá a la rama `main` tras la revisión de código (*Code Review*) y aprobación del Tech Lead (Instructor) y de al menos un compañero.

## 4. Módulos de Desarrollo
El proyecto se compone de **6 módulos diseñados con una arquitectura desacoplada**, uno por estudiante. Cada módulo es una rebanada *fullstack* independiente (modelo en BD + API + interfaz). El diseño prioriza que **ningún módulo bloquee a otro**: si un compañero abandona el curso o se retrasa, el resto del sistema sigue siendo completamente funcional y coherente.

### Módulo 1: Autenticación, Usuarios y Roles (Núcleo)
* **Descripción:** Gestión de sesiones del personal y clientes, y control de acceso por rol.
* **Responsabilidades Fullstack:**
    * Modelos en la BD para `User` y `Role` (Admin, Mesero, Cocina, Cliente).
    * Endpoints para registro, inicio de sesión y cierre de sesión con NextAuth.js.
    * Implementación de Middleware de Next.js para proteger las rutas del panel de administración y las rutas del personal.
* **Punto de desacoplamiento:** Proporciona las funciones de sesión global (`useAuth`) y los IDs de usuario que los demás módulos consumirán de manera pasiva. Es el único módulo que toca la autenticación; el resto asume que la sesión existe.

### Módulo 2: Menú y Categorías - Vista Admin (Núcleo)
* **Descripción:** Panel de administración para la gestión de la carta del restaurante.
* **Responsabilidades Fullstack:**
    * Modelos de `Dish` (platillo) y `Category` (Relación uno-a-muchos).
    * CRUD completo (Crear, Leer, Actualizar, Eliminar) de categorías y platillos (nombre, descripción, precio, disponibilidad, fotos mediante URLs).
    * Formularios validados con Zod para la carga de datos.
* **Punto de desacoplamiento:** Si este módulo se retrasa, otros módulos pueden usar un archivo de datos simulados (*mock data*) respetando el formato del modelo de Prisma.

### Módulo 3: Gestión de Mesas y Reservaciones (Núcleo)
* **Descripción:** Administración de la capacidad física del local: mesas, su ocupación y reservas de clientes.
* **Responsabilidades Fullstack:**
    * Modelos de `Table` (número, capacidad, zona, estado) y `Reservation` (cliente, fecha, hora, nº de personas).
    * CRUD de mesas y endpoints para crear/consultar reservas, evitando dobles reservas en el mismo horario.
    * Interfaz visual del salón (mapa de mesas) con estados Libre / Ocupada / Reservada.
* **Punto de desacoplamiento:** Opera de forma aislada sobre sus propias tablas. La comanda (Módulo 4) puede referirse a una mesa por su **número** sin depender del modelo completo.

### Módulo 4: Comandas y Control de Pedidos (Núcleo)
* **Descripción:** El corazón operativo del restaurante: tomar el pedido de una mesa y seguir su estado.
* **Responsabilidades Fullstack:**
    * Modelos de `Order` y `OrderItem` (relacionados a una mesa y a los platillos).
    * Endpoint para crear una comanda desde una mesa y cambiar su estado (Enviado a cocina → En preparación → Servido → Pagado).
    * Interfaz que permita al mesero armar el pedido (seleccionar platillos y cantidades) y a cocina ver la cola de preparación.
* **Punto de desacoplamiento:** Se conecta a los platillos del Módulo 2 mediante su ID, pero respeta el acuerdo de datos (JSON) pactado en la semana 1; si no hay platillos, puede operar con datos simulados. No gestiona el inventario ni los pagos/estadísticas.

### Módulo 5: Inventario de Insumos de Cocina (Núcleo)
* **Descripción:** Control del stock de ingredientes e insumos que el restaurante necesita en cocina.
* **Responsabilidades Fullstack:**
    * Modelo `Ingredient` con unidades (kg, g, unidades, litros) y un modelo de `StockMovement` o log de entradas/salidas (reposición, mermas, consumo).
    * Interfaz de administración para modificar el stock de un ingrediente y ver el historial de cambios.
    * Lógica para activar alertas visuales en el panel cuando un ingrediente cruce un umbral de "Stock Mínimo".
* **Punto de desacoplamiento:** Es totalmente independiente de los demás flujos: registra entradas y salidas manuales sobre sus propias tablas. No depende de que las comandas le envíen datos.

### Módulo 6: Reportes y Estadísticas de Ventas (Extensión)
* **Descripción:** Dashboard visual de analítica del restaurante para la toma de decisiones.
* **Responsabilidades Fullstack:**
    * Endpoints analíticos que ejecuten agregaciones en la base de datos (ingresos totales, pedidos por día y por mesa, platillos más vendidos).
    * Interfaz con gráficos estadísticos (librerías ligeras como `recharts` o componentes puros CSS/SVG) para mostrar el rendimiento.
    * Mecanismo para exportar un resumen a un formato plano imprimible o CSV básico.
* **Punto de desacoplamiento:** Es un módulo de consumo 100% pasivo (lectura). No altera ninguna tabla ni interfiere con los flujos operativos diarios. Si otras áreas se retrasan, puede visualizar datos de ejemplo.

## 5. Criterios de Éxito y Calificación
Para asegurar el correcto funcionamiento del ecosistema integrado, cada módulo individual será evaluado bajo las siguientes directrices puntuales:

1.  **Funcionalidad en Producción:** La característica asignada debe operar correctamente en el entorno desplegado en Vercel. No deben existir errores críticos en la consola del navegador ni respuestas con código de estado HTTP 500 en el servidor.
2.  **Calidad y Robustez del Código:** Ausencia de variables declaradas y no utilizadas. El tipado en TypeScript debe ser estricto, restringiendo por completo el uso del tipo genérico `any`. Todo el código debe pasar las reglas de formateo estipuladas por ESLint y Prettier.
3.  **Contrato de Datos (Mocking):** En caso de dependencias entre módulos, el estudiante debe demostrar haber acordado y documentado la interfaz de datos (*payloads* JSON) durante la primera semana, usando datos simulados si su contraparte presenta retrasos.
4.  **Colaboración y Code Review:** Participación activa en el flujo de trabajo de Git. Cada estudiante tiene la obligación de revisar, probar localmente y comentar de manera constructiva un mínimo de 2 *Pull Requests* de sus compañeros de clase antes de que el instructor realice el merge definitivo.
